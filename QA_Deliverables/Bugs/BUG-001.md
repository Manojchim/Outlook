## Description

The application determines login state using the browser-readable `sessionStorage` key `stride-demo-authenticated`. Because this value is controlled by the client, any user with browser developer tools or script access can set the key to `true` and reload the application. The UI then exposes the Home, Collection and Running areas without valid credentials.

The root behavior is in [app.js](../../app.js): application visibility is restored when `sessionStorage.getItem("stride-demo-authenticated") === "true"`. No server-side session, token validation or protected API authorization backs this check.

## Steps to Reproduce

1. Open `http://127.0.0.1:4173/`.
2. Confirm that the login screen is visible and the application shell is hidden.
3. Open the browser developer tools console.
4. Execute:
   ```javascript
   sessionStorage.setItem("stride-demo-authenticated", "true")
   ```
5. Reload the page.

## Expected Result

- The login screen must remain visible.
- The application shell and protected navigation must remain hidden.
- Protected application APIs and data must require authenticated server-side authorization.
- Modifying browser storage must not create an authenticated session.

## Actual Result

- The application shell becomes visible after reload.
- The `Welcome Manoj` label is displayed.
- Home, Collection and Running navigation become accessible.
- Authentication is bypassed without entering `admin/admin` or another valid credential.

## Evidence

- Automated Playwright test: [end-to-end.spec.js](../../tests/qa/end-to-end.spec.js)
- Test name: `client-side session state can be set to bypass login`
- Execution: Final Playwright run, 2026-11-18, Chromium.
- Result: Test passed because it successfully demonstrated the unauthorized UI exposure.
- Related detailed test case: `TC-004` in [04_Detailed_Test_Cases.md](../04_Detailed_Test_Cases.md).

## Security Impact

An unauthenticated user can bypass the demo login screen and access client-side application views and public application data. It does not prove server-side access to protected resources; however, it demonstrates that the current authentication control is not an authorization boundary. The implementation is unsafe for use as a real application authentication mechanism.

## Remediation

1. Replace browser-only login state with server-created, securely scoped session cookies or opaque bearer sessions.
2. Require server-side session validation for every protected endpoint and view.
3. Revoke sessions on logout and enforce a server-side session-expiration policy.
4. Mark session cookies `HttpOnly`, `Secure` where HTTPS is used, and `SameSite=Strict` or `Lax` as appropriate.
5. Remove hardcoded credentials and add normal password hashing and account verification for production use.
6. Do not trust `sessionStorage`, `localStorage`, URL parameters or hidden fields for authorization decisions.

## Retest Steps

1. Clear browser storage and open the application.
2. Set `stride-demo-authenticated=true` in `sessionStorage` manually.
3. Reload and verify that protected UI remains hidden.
4. Attempt direct access to protected API routes without a valid server session.
5. Log in through the server, log out, and verify that all session state is revoked.
6. Rerun `TC-004` and confirm that unauthorized access is rejected.
